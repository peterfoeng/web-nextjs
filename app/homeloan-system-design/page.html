Designing the backend for starting a home loan online

A customer fills in a multi-step form over a few days, uploads payslips and ID, then submits it for assessment.

Where we are

Interview order to follow: requirements, then rough estimates, then API and states, then storage, then failures. Always state your assumptions and show that the design doesn't change if they're off by 2×.

1. Requirements

What it must do

  • Create an application; fill in sections over days, on any device
  • Each section saves on its own and can be resumed; data can be incomplete until submit
  • Upload payslips, ID and bank statements; scan for malware and check type and size
  • Submit: validate the whole application, freeze it, hand it to assessment
  • See status, respond to information requests, withdraw

Scale (assumed)

  • ~50k applications a month, ~20k submissions
  • Peak ~100 writes/s (autosave), ~300 reads/s
  • Documents ~6 TB/year, ~40 TB over 7 years
  • 99.9% availability; saves under 300 ms (p95)
Interactive calculator ↓

Protecting personal data

  • Data stays in Australia; Privacy Act, APRA CPS 234
  • TLS everywhere, KMS at rest, extra field-level encryption for TFN and ID numbers
  • Owner-only access for customers; role-based, audited staff access
  • Drafts deleted after 90 idle days; submitted kept 7 years (AML/CTF)
  • No personal data in logs, URLs or events

    What does "3 applications per funded loan" mean?

    It's a conversion funnel: for every loan that's funded, about 3 online applications were started. The rest dropped off.

    • Before submit: just looking, comparing rates, can't borrow enough, upload hassle, abandoned drafts.
    • After submit: declined, low valuation, missed out on the property, went with another lender.

    Why it matters: load comes from applications, not funded loans. That's why drafts expire after 90 days and files from abandoned drafts are deleted.

    Caveats: 14k × 3 = 42k, rounded to 50k in conversation. In Australia ~70% of home loans go through brokers, so a lender's direct online volume could be lower. Either way, the design doesn't change.

    What the numbers mean for the design (what interviewers score)
    1. Low traffic, high value per record. One Postgres primary with a standby is enough. Say "no sharding needed".
    2. Document volume is the real storage problem: object storage with lifecycle tiers.
    3. Plan for spikes (RBA rate decisions, end of financial year): stateless autoscaling servers, per-user rate limits, scanning behind a queue.
    4. Correctness, durability and security matter more than speed: version checks on saves, outbox, encryption.
    Likely follow-up questions

    "What if traffic is 10× higher?" ~1k writes/s: still one larger Postgres. Add read replicas, then partition by application_id if needed. Object storage scales without changes.

    "Why not NoSQL?" State change and outbox event must be one transaction; reporting needs relational queries; JSONB still gives flexible section data.

    "How often should autosave run?" On leaving a section, or every ~30 s while active. Per keystroke is ~10× the writes for no benefit.

    30-second script
    "About 50k applications a month and 20k submits. Peak is around 100 writes per second, so one Postgres primary with a standby is enough. The real volume is documents, about 6 TB a year and 40 TB over the 7-year retention, so they go in object storage with lifecycle tiers. The system is low-traffic and high-stakes, so I'll put the effort into durability and data protection rather than throughput."

      Key headers in depth

      Two different problems: If-Match stops two different edits overwriting each other. Idempotency-Key stops the same request taking effect twice.

      If-Match + ETag: no lost saves (optimistic concurrency)

      The problem: a lost update

      09:00 Laptop loads Income  → version 7
09:01 Phone loads Income   → version 7
09:02 Phone saves 95k      → version 8  ✅
09:03 Laptop saves (stale) → overwrites 95k with 90k ❌

      The fix: send back the version you last saw

      GET  income          → 200  ETag: "7"   store "7"
PUT  If-Match: "7"   → 200  ETag: "8"   store "8" ← replace it
PUT  If-Match: "8"   → 200  ETag: "9"   store "9"
PUT  If-Match: "9"   → 412  another device saved first
      What the GET response looks like
      HeaderPurpose
      ETag: "7"The section's version. Sent back as If-Match. Opaque to the client: a version number or a content hash. Must be strong (no W/ prefix).
      Last-ModifiedOptional and human-friendly; only accurate to the second, so don't use it for the check.
      Cache-Control: no-storePersonal data: nothing should cache it.
      Access-Control-Expose-Headers: ETagEasy to miss: on a cross-origin API, browser JavaScript can't read ETag without it.
      X-Request-IdTracing and support; no personal data.

      Client rules

      1. Replace the stored ETag after every successful save, or your own next autosave gets 412.
      2. One save at a time per section. Queue them; only the newest data matters.
      3. On 412, never auto-retry with the new ETag. That overwrites the other change. Fetch the latest and let the user choose.

      Where the version lives

      • Server: an integer version column per section; the ETag is built from it. Saves run UPDATE … SET version = version + 1 WHERE … AND version = $ifMatch; 0 rows → 412.
      • Client: in memory, next to the section's data (a ref or a query cache). Reload → just GET again.
      • Offline drafts: store the ETag with the unsaved data, so a stale draft triggers a merge prompt days later.
      • Not in a cookie, a global, or localStorage on its own.
      Version each section separately Optimistic, not locking: drafts stay open for days Missing If-Match → 428

      Idempotency-Key: submitting twice has the same effect as once

      The problem: the server commits the submit, but the network drops before the response arrives. The app retries, or the customer clicks again. Without a key, the retry gets a 409 (or worse, the work runs twice) and the customer sees an error for a submit that worked.

      POST /applications/123/submit
Idempotency-Key: 9f1c2a7e-…   ← UUID made once per click
→ (network drops after commit)

POST /applications/123/submit
Idempotency-Key: 9f1c2a7e-…   ← same key on retry
→ 202 { "status": "SUBMITTED" }  ← stored first response

      On the server (idempotency_keys, unique on user + key)

      1. Insert the key in the same transaction as the state change and outbox event.
      2. Key exists, same request hash → return the stored response.
      3. Key exists, different request → 422.
      4. First request still running → 409, or wait briefly.
      5. Delete keys after ~24 hours.
      If-Match (ETag)Idempotency-Key
      Protects againstTwo different edits overwriting each otherThe same request applied twice
      Used onSaving a section (PUT)Submit, withdraw, create (POST)
      Client sendsThe version it last readA UUID per user action
      On conflict412: reload and mergeStored response; 422 if reused for different work
      "ETags with If-Match give optimistic concurrency, so saves from two devices can't silently overwrite each other. Idempotency keys make submit safe to retry, which matters because mobile networks drop responses after the server has already committed."

      5. Documents in object storage, with lifecycle tiers

      Why not keep files in Postgres?

      • ~40 TB makes backups, restores and replication slow; failover could take hours.
      • Database storage costs ~5–10× more per GB.
      • Every upload would pass through the app servers.

      What goes where

      • Postgres: one small row per document: doc_id, application_id, type, size, sha256, storage_key, status, scan_result.
      • Object storage: the file itself.
      • Browser uploads straight to object storage with a pre-signed URL.

      Retention clock starts when the loan settles or is declined, not at upload. Tag each object with its retention date when the decision is made.
      Object Lock (compliance mode) stops anyone, admins included, deleting or changing files during retention. Legal holds override expiry during disputes.
      Archive retrieval takes hours. Fine for audits; say it out loud.
      IA tiers have minimum storage periods and retrieval fees, so don't move files there too early.

      What is a pre-signed URL?

      A link to one object in a private bucket, already signed with the server's credentials. Whoever holds it can do one thing, for a limited time, without AWS credentials of their own.

      1. Server signs method, bucket, key and expiry, locally, with no call to AWS.
      2. Browser uses it to talk to S3 directly.
      3. S3 recomputes the signature; anything changed or expired → 403.

      Caveats: anyone holding it can use it until expiry; you can't revoke one URL; never log full URLs. Azure: SAS token. GCP: signed URL.

      One bucket, many keys (not a bucket per user)

      flowchart LR
  A[User A] -->|URL signed for app-111/doc-aaa only| K1[app-111/doc-aaa]
  B[User B] -->|URL signed for app-222/doc-ccc only| K3[app-222/doc-ccc]
  A -. edits key to app-222 .-> X[403 signature mismatch]
  subgraph Bucket[quarantine-bucket]
    K1
    K2[app-111/doc-bbb]
    K3
  end
      • The API checks ownership and chooses the key itself.
      • Users can't list the bucket or touch other keys.
      • A bucket per user fails: ~100 bucket default limit, config sprawl, and no added security.
      • Separate buckets by trust level instead: quarantine, clean, infected.
      Pre-signed POST rather than PUT: a POST policy lets S3 enforce content-length-range and content type. A PUT URL can't cap the size.
      Multiple files: one API call registers all of them, then upload with at most ~3 in parallel. Each file succeeds, fails and retries on its own.
      Cap files per application (e.g. 30) plus per-user rate limits.
      Don't zip: zip bombs, harder to scan, one bad file rejects everything.
      No personal data in keys: use {applicationId}/{docId}, never filenames or names.
      Use the S3 event as the source of truth, not a "complete" call from the browser, which may close before sending it.

      7. Malware scanning

      Why scan? Uploaded files are untrusted and assessors open them on bank computers. Risks: PDFs with scripts, executables renamed .pdf, zip bombs, password-protected files the scanner can't open.
      OptionWhat you buildWhen
      1. Managed (GuardDuty Malware Protection for S3 / Defender for Storage) say firstNo scanner. AWS scans, tags the object, sends an event. A small Lambda moves the file and updates the DB.Default: buy before you build
      2. Container service (ECS Fargate / Kubernetes)Worker container + ClamAV sidecar (clamd); reads the queue, streams each file to clamd.Own engine, CDR, custom rules
      3. Lambda + ClamAV imageSame worker in LambdaLow volume only: cold starts reload ~1 GB of signatures (10–30 s)

      • Take a message; claim the row (SCANNING) with a conditional update
      • Fail closed if virus definitions are older than 24 h
      • Download from quarantine (≤ 20 MB fits in memory)
      • Antivirus: stream bytes to ClamAV → OK or FOUND <signature>
      • Structure checks: first bytes match the type, no encrypted PDFs, no scripts or embedded files, no pixel bombs
      • Optional CDR: rebuild the file without active content
      • Sort: clean / infected / invalid; on error don't acknowledge, so it retries then goes to the DLQ

      Code layout: apps/web, apps/api, services/doc-scanner, packages/shared. The scanner deploys separately so it scales and fails on its own.

      Why a queue in front of scanning?

      1. Speed: scans take 2–30 s; the upload returns immediately.
      2. Spikes: the queue gets longer; nothing is lost. Scale workers on the age of the oldest message.
      3. Isolation: scanner down ≠ form saving down.
      4. Retries: crashed messages reappear; after ~5 attempts → DLQ + alert.

      Sizing: 2 uploads/s × 5 s per scan ≈ 10 concurrent scans → 3–5 workers, up to ~20 in spikes. Target: 95% scanned within 60 s.

      Correctness

      • At-least-once delivery: scanning twice is harmless; status updates are conditional (WHERE status = 'SCANNING').
      • Fail closed: submit blocked while scanning; only the scanner reads quarantine; assessors read only the clean bucket; stale definitions stop the worker.
      • Copy → DB → delete: a crash at any point can be retried safely; leftovers expire from quarantine after 24 h.
      • Reconciliation job every 15 min for files stuck in PENDING_UPLOAD (events can be lost).
      • Tag-based backstop: deny GetObject unless tag = NO_THREATS_FOUND.
      • KMS: GuardDuty's role needs kms:Decrypt, or every scan is ACCESS_DENIED.

      Object tags vs metadata

      Object: quarantine/app-111/doc-aaa
      ├── Data: the PDF bytes (never touched)
      ├── Metadata: Content-Type, size, ETag (fixed at upload)
      └── Tags: GuardDutyMalwareScanStatus = NO_THREATS_FOUND (change any time)
      • Up to 10 key–value pairs per object, stored next to the file.
      • Adding a tag doesn't re-upload the file.
      • Bucket policies and lifecycle rules can use tags.

      FailureHow it's handled

      Where you stand out

      1. One application service for every channel: app, NetBank, branch, brokers.
      2. Most applicants are already customers: identity already verified (skip ID upload); salary visible (pre-fill income, payslips optional).

      Regulation to mention briefly

      • APRA CPS 234: information security: encryption, access control, testing.
      • APRA CPS 230: operational resilience. Origination is likely a critical operation: recovery targets, tolerance for disruption.
      • NCCP responsible lending: why income and expenses must be verified (payslips).
      • Privacy Act, AML/CTF: data minimisation, draft expiry, 7-year retention.
      45-second script

      "Let me anchor on CBA. The market funds roughly 70k home loans a month, and CBA has about a quarter of that, so around 17k funded. If roughly 3 applications are started for every loan funded, and I build one application platform shared by the app, web, branch and broker channels, that's about 50k applications a month, peaking around 100 writes per second. That's comfortable for a single Postgres primary. The bigger issues are document storage and data protection.

      CBA's advantage is that most applicants are existing customers. We've already verified their identity, and we can see their income in their accounts. So I'd pre-fill the form and make uploads the exception, using CDR data from other banks where we can. That reduces both friction and risk.

      Origination is probably a critical operation under CPS 230, so I'll design for resilience: idempotent submits, an outbox for events, and multi-AZ."
